# 卡片 39 方案评审：全局截图即录入口

> 状态：**待用户确认**（R63 评审产出；确认后按 §5 施工，未确认不写代码）
> 背景：产品灵魂是「截图即录」，但当前链路要「切窗口→找标签→按 C→粘贴」，每多一步都在流失（UX 复盘第一大流失点）。

## 1. 目标场景

测试人员在全屏应用/游戏/IDE 里发现缺陷 → 用**习惯的系统截图工具**（微信/QQ 截图、Snipaste、PrintScreen）截图（此时剪贴板已有图）→ **不切窗口**，一个全局快捷键直接唤起轻量录入浮层 → 图已在剪贴板自动带上 → 补一句描述 → 回车发送 → Toast 确认 → 继续手上的事。

关键修正（相对初期设想）：**截图动作交给用户已有的系统工具**，我们要做的不是「再做一个截图器」，而是把「唤起→粘贴→发送」这三步压到一个快捷键里。

## 2. 候选方案对比

| 方案 | 优势 | 硬伤 | 结论 |
| --- | --- | --- | --- |
| A. Chrome/Edge 扩展（MV3） | 分发简单（加载已解压即用）；复用现有 REST API 与密钥体系；零构建链（原生 JS）；不动主程序 | 全局快捷键仅浏览器运行时有效；截不了其他应用的屏（但我们不需要它截） | **推荐** |
| B. 托盘小程序（Tauri/Electron） | 真全局快捷键+托盘常驻+可截图 | 新增 Rust/构建链；安装包分发与版本同步成本；对开源用户门槛高 | 留作阶段二 |
| C. 系统快捷键+CLI（Shortcuts/Automator） | 无新组件 | 跨平台差、配置门槛高、无 UI | 否 |

## 3. 推荐方案的最小可用范围（MVP）

**安装与配置**（一次性）：
- `chrome://extensions` → 开发者模式 → 加载已解压的 `vibehub/extension/`
- 扩展 options 页：服务器地址（默认 `http://127.0.0.1:3210`）+ VibeHub 密钥（复用 MCP 密钥，需 `bug:write` scope）→ 存 `chrome.storage.sync`

**日常使用**（三步）：
1. 系统工具截图 → 全局快捷键（默认 `Alt+Shift+V`，`commands` 可改）唤起录入浮层
2. 浮层自动读取剪贴板图片（`navigator.clipboard.read()`）→ 缩略图预览；标题输入框 autofocus；可选描述
3. `Ctrl/⌘+Enter` 发送 → `POST /api/upload`（multipart）→ `POST /api/bugs`（attachment_ids 关联）→ Toast「已创建 bug_xxx」→ 浮层自动关闭

**权限最小化**：`storage`（配置）、`clipboardRead`（读图）、`notifications`（Toast 降级）；`host_permissions` 仅用户配置的服务器地址。**不要** `activeTab`/`tabs` 全量/`captureVisibleTab`。

## 4. 与主程序的边界

- 扩展是**独立客户端**：只消费现有 REST API，零数据库接触、无新后端接口、无 schema 变更
- 鉴权用现有 MCP 密钥体系（Bearer + `bug:write` scope）——密钥在密钥页创建，扩展 options 里粘贴
- 代码位置：`vibehub/extension/`（独立 `manifest.json` + 原生 JS/CSS，不接入 npm workspaces 构建；可选 TS 但不引构建链）
- 项目归属：MVP 用 options 里配置的默认项目；AI 侧 `get_project_context(project_slug)` 已有按 slug 匹配能力，人在扩展里不需选项目

## 5. 已知限制（如实告知用户）

1. **全局快捷键仅在浏览器运行时有效**（MV3 平台限制）——测试场景浏览器常驻可接受；真全局需求是方案 B（托盘版）的立项理由
2. `clipboardRead` 依赖浏览器支持（Chrome/Edge ✔；Safari 扩展另计）；剪贴板无图时浮层引导「先用系统截图工具截图」
3. 分发形态：开源用户走「加载已解压扩展」开发者模式（README 给图文引导）；上架商店是后续运营事项
4. **本环境 IAB 无法安装扩展**——实现轮的验收需在真实 Chrome 加载（或 Playwright `--load-extension` 自动化冒烟：配置→触发命令→断言 API 侧缺陷创建）
