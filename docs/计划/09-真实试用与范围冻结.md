# 09 真实试用与范围冻结（R77 起）

> 状态：**生效中**（R77 由用户授权代为决策）。试用结束评审前，本文件优先于「继续加功能」的一切计划。
> 施工清单不在本文件重复维护，以 `PROGRESS.md` §2 为唯一来源（禁止双轨）。

## 1. 为什么冻结

- R76 修掉的两个 P0（截图 401/404、MCP 写错项目）都是「真用一天就会暴露」的问题，却在 70 轮施工、全绿测试下潜伏；截至 R77，验收库 0 个缺陷、0 次 MCP 调用。
- 结论：下一步的价值不在功能数量，而在让「截图录入 → AI 经 MCP 读取 → 修复回填 → 看板同步」这条闭环接受真实使用的检验。

## 2. 冻结范围（结束评审前有效）

| 类别 | 处理 |
| --- | --- |
| 卡片 51（看板表格视图）及任何新功能卡 | **冻结**，不施工 |
| 卡片 39（全局截图入口） | **已砍**（见 `39-全局截图入口方案.md` §7） |
| 试用反馈缺陷（`trial` 标签） | **最高优先**，按录入先后处理 |
| 验证补齐、E2E、安全/性能/运维加固、文档纠偏 | 允许，按 `PROGRESS.md` §2 顺序 |

**判定标准**：会给用户新增可见功能、入口或配置项的，一律算新功能；新想法只登记 `PROGRESS.md` §4「试用后评审」，不施工。

## 3. 试用方式

- **时长**：10 个工作日（国庆等假期不计），从合入 R76 修复后第一次实际使用当天起算；起始日记入 `PROGRESS.md` §1。
- **形态**：本机 `npm run dev:server`（:3210，连验收库）；IDE Agent 按 README「连接 IDE Agent」的 **SSE 方式**接入（交付形态同款传输）。密钥 scope：`context:read`、`attachment:read`、`attachment:write`、`bug:write`。
- **试用项目**：手上正在开发的真实仓库；若只有 VibeHub 本身，就用 VibeHub 追踪 VibeHub。
- **节奏**：每个工作日至少用截图录 2 个缺陷，并让 IDE 里的 AI 通过 MCP 处理其中 1 个（读取 → 修复 → `update_bug_status` 回填）。
- **摩擦记录**：用着不顺手的地方，直接在 VibeHub 里录成缺陷并打标签 `trial`（录入本身也是试用）。掉线、写错项目、截图没显示这类问题务必记录。

## 4. 成功标准

结束时运行 `bash server/scripts/trial-metrics.sh <起始日期>`（只读）核对：

| 指标 | 目标 |
| --- | --- |
| 截图录入的缺陷（人工创建且带图片） | ≥ 20 |
| AI 经 MCP 推进到 resolved 的缺陷 | ≥ 人工新建缺陷的 50% |
| 刷新令牌重放触发次数（`auth.token_reused`） | 0 |
| 写错项目 | 0（脚本输出 AI 建单的项目分布，人工核对） |
| MCP 调用失败率 | 仅记录（参数错误、非法流转属正常失败） |

另附主观产出：`trial` 摩擦清单，按出现次数排序。

## 5. 结束评审（决定解冻什么）

- **达标**：按摩擦清单排序决定下一批卡片。卡片 51 仅在「看板找缺陷难 / 列信息不够」进入摩擦前三时解冻。
- **卡片 39 重开**：摩擦清单中「懒得切回 VibeHub 而没录 / 录入太慢」类记录 ≥ 3 次，且先完成 REST 鉴权方案评审（见 39 文档 §7）。
- **未达标（录入量不足）**：先分清是「没用起来」还是「用不下去」，对症处理；**不以加功能来解决**。
- 评审结论写入 `PROGRESS.md` §3/§4，并更新本文件状态为「已结束」。
